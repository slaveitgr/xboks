# wine-uwp feasibility for XBOKS

Reviewed `designgears/wine-uwp` at commit [`ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767`](https://github.com/designgears/wine-uwp/tree/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767), on 2026-10-22. This was a source and documentation review. No repository setup scripts, ISO download, harvest, Wine build or application launch were run.

The project is a relevant experimental runtime candidate for XBOKS. It addresses the UWP activation, WinRT, XAML and DirectComposition requirements identified in [the actual Real Drive Simulator package](real-drive-simulator-package.md). That is substantially more than a package extractor. It is not yet a validated runtime for this game or for XBOKS, and should be evaluated separately from the existing MSIXVC/Proton runtime.

## What the pinned source provides

- A partial source overlay for Wine, including new `wineuwp`, `appxinstall`, app-model and composition implementations. The [recorded Wine base](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/BASE.txt) is Wine 11.20, upstream commit `7298a818b79446bae153b8d5aa27235ab3703bf9`, with project Wine HEAD `07568d2928f0ed93d5c09f83513ce6beb8cad2ae`. A complete upstream Wine source/build is still required.
- `wineuwp-install`, `wineuwp-setup` and `wineuwp-launch` programs, with package identity, app activation, framework graph, prefix registration and CoreMessaging setup. The [host launcher](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/run.sh) explicitly selects X11 graphics for these apps.
- Local Windows components: XAML, CoreMessaging, app-model DLLs, framework packages, fonts, metadata, globalization data and the SOFTWARE registry hive. These are harvested from a Windows image and are not reimplementations supplied under Wine's license.
- Stand-ins for selected Windows services implemented under Wine DLL modules, including game-platform, authentication and WebView hosting components. The README's `shims/` link is stale at this pin: that directory contains no tracked files; the findings document their migration into Wine modules.

The [package instructions](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/packaging/README.md) describe a product layer that supplies its own UI and branding. This makes a separate XBOKS runtime adapter a plausible integration shape; adopting the original Windows Xbox application as XBOKS's UI is not required.

## Reported app results and their limits

The [README](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/README.md) reports interactive Shapr3D, Solitaire, Calculator, Feedback Hub, Media Player and Halo Infinite results, and a Camera error page. The repository includes screenshots and extensive investigation notes. These are upstream reports, not results reproduced on the XBOKS machine. No Real Drive Simulator test was found.

The latest Wine 11.20 section in [Findings-M4](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/docs/Findings-M4.md#2026-10-21-wine-1120) needs to be read alongside the README. Its comparison records the same imperfect test-prefix baseline on 11.17 and 11.20: Calculator image difference `AE 3924.73`, Media Player `236` colors, and Feedback Hub, Solitaire and keyboard checks failing on both. It also records manual Xbox/Halo/Shapr3D screens after the upgrade. Those observations support progress and parity with that test setup; they do not constitute a completely passing fresh-runtime compatibility suite.

The [regression script](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/regress.sh) checks screenshots, color counts and selected log milestones. It prints outcomes but does not aggregate every failure into a final nonzero exit status. Its reported front-end success is also narrower than a sustained gameplay/input test. XBOKS needs its own explicit acceptance criteria and failure gates. Recent findings also retain WebView2 purchase-dialog rendering limitations; the WebView2 declarations in Real Drive Simulator's manifest therefore require specific testing.

## Licensing and payload provenance observed

| Component | Explicit evidence at this pin |
| --- | --- |
| Modified/new Wine modules | [wine/README licensing section](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/README.md#licensing) states LGPL-2.1-or-later for these copies and new Wine files. Representative `wineuwp`, `dcomp`, `appxinstall` and launcher/setup/install C sources contain matching notices. |
| Host packaging Python/shell scripts | No repository-root `LICENSE`, `COPYING` or `NOTICE`, or explicit blanket license covering these scripts, was found. Their public availability alone does not establish the same license as the Wine modules. |
| Microsoft DLLs/frameworks/fonts/hive | The project deliberately keeps them outside Git and its distributable runtime tree. Its [clean-check script](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/check-clean.sh) rejects Windows payloads, app packages and large binaries. No redistribution permission for these payloads is established by the repository's Wine notices. |

This records the notices and project behavior actually found; it is not a legal determination. Any distributed Wine candidate must retain its applicable notices and corresponding source/build provenance. Host scripts need established licensing coverage before copying them into a distribution. The conservative integration boundary is an independently implemented adapter to a separately obtained runtime, with Windows components provided locally rather than placed in XBOKS release assets.

Microsoft's [Evaluation Center](https://www.microsoft.com/en-us/evalcenter/evaluate-windows-11-enterprise) describes the Enterprise image as a 90-day evaluation. A downloadable evaluation image does not by itself establish unrestricted redistribution or indefinite production-use terms for harvested components. The exact image and applicable terms need to remain visible to anyone choosing this experimental setup.

## Setup requirements and gaps to close

The [ISO downloader](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/packaging/harvest/download_iso.py) follows a Microsoft Evaluation Center redirect. Its tested image is Windows 11 Enterprise evaluation 25H2, build `26200.6584`, en-US:

- Size: `7,092,807,680` bytes, approximately `6.61 GiB`.
- Pinned SHA-256: `a61adeab895ef5a4db436e0a7011c92a2ff17bb0357f58b13bbc4062e535e7b9`.
- Downloads resume through a `.part` file. A known-size image with the wrong hash is deleted. An unknown-size image is labeled `UNVERIFIED` but still returns success; XBOKS should not convert that result into a verified/ready runtime.

The [harvester](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/packaging/harvest/harvest.py) requires Python 3 and `7z`, `7zz` or `7za`. It extracts `sources/install.wim`/`install.esd` to temporary storage, selects an image containing Windows, then extracts its manifest paths. The current manifest has 2,690 non-comment entries, including entire matching x64 framework directories. Missing entries are written to `harvest-missing.txt`; the script does not itself fail simply because required components are missing. A readiness check must validate required files, versions and generated registrations rather than trust process exit alone.

Further requirements include a Wine 11.20 build and its normal build dependencies, `autoreconf`, compiler/toolchain support, and additional disk space for full source/build output, ISO, extracted WIM/ESD, harvested files and prefix. The separate probe build uses CMake, clang-cl/lld-link and Windows SDK material from xwin. Some launcher setup resolves DLL-specific public symbols from `msdl.microsoft.com`; the generated addresses are bound to each DLL's image stamp and size. WebView2 runtime support is separately supplied when present.

No ISO download or build was initiated. The ISO's size alone understates the temporary and compiled storage requirement. Budget for the extracted WIM/ESD, harvested components, prefix and source/build tree before starting the complete experiment.

## Safe XBOKS integration experiment

1. Register a distinct experimental runtime selection with an immutable source/build pin. Keep the existing Engine runtime and installed-game behavior intact.
2. Use a dedicated data directory, prefix, staging root and build tree. Set `WINE_UWP_DATA`, `WINEPREFIX`, `UWP_BIN`, `WIN11`/`WINE_UWP_WINDOWS_TREE`, `WINE_BUILD` and `WINE_UWP_GAMES_DATA` consistently. The upstream wrapper derives its prefix from its data directory, and `run.sh` terminates that prefix's wineserver before a run; overriding only one path does not provide complete isolation.
3. Accept explicitly selected local Windows material or a separately reviewed acquisition flow. Require an accepted image/hash, complete required-file inventory, matching symbol information and dependency versions. Do not bundle Windows payloads into the XBOKS runtime release.
4. Stage the already verified Real Drive Simulator x64 package into the experimental area, preserving its identity, WinRT activation and framework graph. Do not silently treat lower-than-declared framework versions as satisfying the package's requirements.
5. Test package setup and then a bounded app launch on an isolated display/prefix. Require actual rendered application content, responsive controls and clean shutdown; a window, splash screen or successful extraction is insufficient. Record the exact runtime/package hashes and any unsupported API/class before changing the product's installability.

No part of this review proves Real Drive Simulator launches or plays. The upstream project provides concrete machinery that makes such a test worthwhile; the next step is a reproducible isolated candidate and real acceptance, rather than a claim that all UWP games work.

## Runtime integration audit

The current XBOKS runtime recipe pins Wine `b1dd32734a34472a28eb5be9922df06e07ac0834` and its own GDK/account bridge in [`runtime-patches.lock.json`](../../scripts/runtime-patches.lock.json). The reference overlay targets Wine 11.20 and replaces whole source files, including `ntdll`, `kernelbase`, `combase`, `win32u`, DXGI and DirectComposition. Copying those files over the existing runtime would combine two different Wine bases and replace already validated Engine behavior. A separate candidate runtime and launcher adapter is the appropriate boundary.

The activation and rendering code contains substantive implementations:

- [`wineuwp-launch/main.c`, lines 320–398](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/programs/wineuwp-launch/main.c#L320-L398) reads package identity and launch settings, creates the package's storage registry key, starts CoreMessagingRegistrar, then creates and waits for the actual application process. [`kernelbase/version.c`, lines 1555–1873](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/kernelbase/version.c#L1555-L1873) supplies identity and a package graph from that environment. These are compatibility identities, not a Windows deployment database or an AppContainer isolation guarantee.
- [`wineuwp/main.c`, lines 1690–1885](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/wineuwp/main.c#L1690-L1885) drives private native `twinapi.appcore` view activation and marks the otherwise absent process-state manager as registered. Symbol lookup checks the loaded DLL's timestamp and image size; its built-in fallback addresses apply only to a specific Windows build. [`wf_CreateCoreWindow`, lines 4565–4610](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/wineuwp/main.c#L4565-L4610) calls native `Windows.UI.dll` ordinal 1500 and connects navigation, text input and the compositor. This route depends on those Windows components and their private ABI.
- [`dxgi/compswapchain.c`](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/dxgi/compswapchain.c#L21-L55) implements D3D11 composition buffers and presented-frame copies; [`dcomp/composition.c`](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/dcomp/composition.c#L1279-L1557) paints the visual tree with texture readback, CPU rasterization and GDI blits. That is a real rendering path, with a different performance profile from native Windows composition. It needs measurement on the target game's UI and graphics path.

Several compatibility assumptions must remain explicit:

| Pinned implementation | Integration consequence |
| --- | --- |
| [`xgameruntime/store.c`, lines 63–112](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/xgameruntime/store.c#L63-L112) returns an active game license, dummy SKU, an acquired handle of `(void *)1`, and a licensable result. [`IsLicenseValid`, lines 201–204](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/xgameruntime/store.c#L201-L204) only checks that the handle is non-null. | These are stand-ins, not verified entitlement or expiration results. XBOKS retains its authenticated, signed Engine entitlement checks; this Store implementation must not replace them. The reference's separate real SISU/XSTS sign-in does not make these hardcoded license answers authoritative. |
| [`dcomp/composition.c`, lines 2378–2385 and 3932–3938](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/dcomp/composition.c#L2378-L2385) installs an x64 exception handler by default and continues certain null-page execute faults through a synthetic return. | A process staying alive can conceal an unimplemented or invalid call. Acceptance must require working application content and input, and record these faults. |
| [`appxinstall/install.c`, lines 1006–1033](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/appxinstall/install.c#L1006-L1033) falls back to a framework older than the declared minimum; [`manifest.c`, lines 87–119](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/appxinstall/manifest.c#L87-L119) selects the first application without classifying its activation model. | XBOKS's namespace-aware inspection and dependency requirements remain the admission criteria; staging is insufficient proof of compatibility. |
| [`winexboxauth/webaccount.c`, lines 733–745](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/winexboxauth/webaccount.c#L733-L745) completes Store sign-out while retaining the account; [`windows.services.store/main.c`, lines 22–27](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/windows.services.store/main.c#L22-L27) describes most Store methods as unimplemented. | Account separation, sign-out and Store purchase/license behavior need their own implementation rather than adoption of the shim's successful completion. |

Some code is deliberately title-specific: the launcher enables native syscall handling when `EasyAntiCheat/Settings.json` exists, and [`winexboxauth/auth.c`, lines 1680–1739](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/dlls/winexboxauth/auth.c#L1680-L1739) adds Halo Waypoint relying-party/signature handling. Those paths are not evidence of general UWP or anti-cheat compatibility.

The source can be evaluated in two stages. A clean, pinned Wine 11.20 tree plus the overlay can be compiled without a Windows ISO: the relevant Wine modules link to Wine import libraries, and `wineuwp` is explicitly x64-only. This can verify source completeness, compiler compatibility, exports and isolated synthetic identity/activation failures. It does not validate an actual UWP UI. The current [`wineuwp-setup` native-module list, lines 66–82](https://github.com/designgears/wine-uwp/blob/ca32ef4a0078a8fe7a7da1f1d0a73014fb3ab767/wine/programs/wineuwp-setup/main.c#L66-L82) needs Windows XAML, UI, `twinapi.appcore`, CoreMessaging, ApplicationModel, MRT/globalization and related modules; package installation also takes a Windows tree and resolves framework packages from it. The actual Real Drive Simulator test therefore requires the validated local Windows/framework material and matching symbol/registry data described above. No such build or acceptance was performed during this audit.
